# Enlaight — OpenAPI / API Documentation

This document describes how the REST API contract is defined, served, and
consumed in Enlaight, and catalogues the error responses clients can expect.

> TL;DR — there are two parallel surfaces:
>
> 1. **Static spec**: [openapi.yml](../openapi.yml) at the repo root — a
>    hand-maintained OpenAPI 3.0.3 document, used as the human-readable API
>    reference.
> 2. **Live schema**: `/swagger/` — auto-generated by
>    [drf-yasg](https://drf-yasg.readthedocs.io/) from decorators on the
>    Django views, served as Swagger UI (OpenAPI 2.0 under the hood).
>
> They cover the same endpoints but are produced by different pipelines. Keep
> both in mind when changing the API.

---

## 1. The static spec — `openapi.yml`

Path: [openapi.yml](../openapi.yml)

- **Format**: OpenAPI 3.0.3
- **Scope**: all public `/api/*` routes plus `/health/`
- **Maintenance**: edited by hand alongside view changes
- **Consumers**: humans, Postman/Insomnia imports, and any external client
  that wants a stable reference. The frontend does **not** run a code
  generator against it — it is documentation, not a build input.
- **Security scheme**: `BearerAuth` (HTTP bearer, JWT)
- **Servers**: `http://localhost:8000` (dev), `https://api.enlaight.ai` (prod)

### Structure

The file is organised in the standard OpenAPI layout:

- `info` — title, description, version
- `servers` — dev and prod base URLs
- `components.securitySchemes.BearerAuth` — JWT bearer
- `components.schemas` — reusable request/response shapes
  (e.g. `LoginRequest`, `UserProfile`, `Agent`, `KBCreateRequest`,
  `PaginatedResponse`, `Error`)
- `tags` — logical groupings (`Auth`, `Users`, `Projects`, `Agents`,
  `Knowledge Base`, `Chat Sessions`, `Search`, `Translation`, `Health`, …)
- `paths` — operations, each declaring `tags`, `operationId`, `requestBody`,
  `parameters`, `responses`

### When to update

Update [openapi.yml](../openapi.yml) whenever you:

- add, rename, or remove a route
- change a request or response shape
- add or remove a required field
- change auth requirements for an endpoint

The file is not generated, so there is no script to run — the edit is part
of the same PR as the view change.

## 2. The live schema — `drf-yasg` and `/swagger/`

Enlaight uses [`drf-yasg`](https://drf-yasg.readthedocs.io/) (pinned at
`>=1.21.10,<2.0.0` — see [backend/pyproject.toml](../backend/pyproject.toml))
to introspect Django REST Framework views and expose a browsable schema.

### Registration

- App registered in `INSTALLED_APPS` — [backend/src/core/settings.py:114](../backend/src/core/settings.py#L114)
- Swagger bearer scheme declared in `SWAGGER_SETTINGS` — [backend/src/core/settings.py:149-159](../backend/src/core/settings.py#L149-L159)
- Static assets shipped from the `drf_yasg` package and served by WhiteNoise
  — [backend/src/core/settings.py:22-27](../backend/src/core/settings.py#L22-L27)
- URL wiring — [backend/src/core/urls.py:12-45](../backend/src/core/urls.py#L12-L45)

### UI endpoint

| URL | What it serves |
|-----|----------------|
| `GET /swagger/` | Swagger UI (interactive) |

For local dev: http://localhost:8000/swagger/.

`drf-yasg` also exposes JSON/YAML forms of the schema when
`schema_view.without_ui(...)` routes are added, but those are **not wired
up** in this project — only the UI route exists.

### Access control

Access to `/swagger/` is gated by the `SWAGGER_REQUIRE_AUTH` environment
variable (see [env.sample:51-53](../env.sample#L51-L53)):

- `SWAGGER_REQUIRE_AUTH=False` — schema is public, no auth required.
  This is the default when `DEBUG=True`.
- `SWAGGER_REQUIRE_AUTH=True` — requires a Django admin user
  (`permissions.IsAdminUser`). This is the default when `DEBUG=False`.

Rationale: in production we do not want to leak the full API schema to
unauthenticated visitors. Flip the flag to `False` if you want to expose
public API docs for a given deployment.

### Per-view annotations

Each view is decorated with `@swagger_auto_schema` to describe its
operation, request body, parameters, responses, and tags. Examples:

- Simplest: [backend/src/core/views.py](../backend/src/core/views.py) — the `/health/` endpoint
- Function view: [backend/src/authentication/views/authentication.py:305-316](../backend/src/authentication/views/authentication.py#L305-L316) — `LoginView`
- Proxy view with file upload: [backend/src/authentication/views/kb_file_add.py:25-38](../backend/src/authentication/views/kb_file_add.py#L25-L38)

Common fields used:

```python
@swagger_auto_schema(
    tags=["Auth"],
    operation_id="login_user",
    operation_summary="...",
    operation_description="...",
    request_body=LoginSerializer,          # serializer or openapi.Schema
    manual_parameters=[...],               # for path/query params
    consumes=["multipart/form-data"],      # when uploading files
    responses={
        200: openapi.Response("OK", SomeSerializer),
        400: openapi.Response("Validation error"),
        401: openapi.Response("Unauthenticated"),
    },
    security=[{"Bearer": []}],             # or [] to mark public
)
```

Note that `drf-yasg` emits **OpenAPI 2.0 (Swagger)**, while the hand-written
[openapi.yml](../openapi.yml) is OpenAPI 3.0.3. They are not byte-for-byte
comparable, but they describe the same surface.

## 3. Authentication

All authenticated endpoints use a JWT bearer token:

```
Authorization: Bearer <access_token>
```

- `POST /api/login/` returns an access token (in the JSON body) and sets the
  refresh token as an `httpOnly`, path-scoped cookie on `/api/refresh/`.
- Access tokens have a 2-hour lifetime; refresh tokens have a 1-day lifetime
  (see [backend/src/core/settings.py](../backend/src/core/settings.py) under `SIMPLE_JWT`).
- `POST /api/refresh/` rotates the pair; the old refresh token is blacklisted.
- `POST /api/logout/` blacklists the current refresh token.

Endpoints that set `security=[]` in their decorator are explicitly **public**
(login, signup, refresh, logout, password reset, public role listing).

## 4. Error responses

### Canonical shape

All error responses return JSON with a single `detail` field:

```json
{ "detail": "Projeto não encontrado." }
```

This matches the `Error` schema in [openapi.yml](../openapi.yml) and DRF's
own conventions (`NotFound`, `PermissionDenied`, and the default
`ValidationError` rendering all produce `{"detail": ...}`).

**Convention**: always return `{"detail": "..."}` from new views. Do not
introduce `{"error": ...}` — clients read `response.data.detail` everywhere
and a mismatched key silently falls back to generic text.

DRF validation errors (raised via `serializer.is_valid(raise_exception=True)`)
are the one exception: they return a field-keyed dictionary instead, which
is DRF's built-in behaviour:

```json
{ "email": ["Enter a valid email address."] }
```

### Status codes used across the API

| Status | When it is returned |
|--------|---------------------|
| `200`  | Success |
| `201`  | Resource created |
| `204`  | Resource deleted (no body) |
| `207`  | Partial success — e.g. `PATCH /api/kb/file/update/` when the new file uploaded but the old file could not be removed |
| `400`  | Validation error, missing required query/body fields, invalid/expired token on password reset and invite confirmation, duplicate names on `POST /api/clients/` and `POST /api/bots/` |
| `401`  | Missing or invalid credentials (`/api/login/`), invalid/expired refresh token (`/api/refresh/`), invalid JWT on any authenticated route |
| `403`  | Authenticated but not permitted — e.g. non-admin calling `POST /api/invite/`, user without project access on KB endpoints, `POST /api/login-as/{user_id}/` without admin |
| `404`  | Target resource not found — user, project, client, agent, KB, chat session |
| `413`  | `POST /api/i18n/translate/batch/` received too many items or text too long |
| `500`  | Required configuration missing — e.g. `N8N_BASE_URL` / `N8N_KB_KEY` unset when a KB proxy view is called; unexpected server failure during JWT generation |
| `502`  | Upstream (n8n) returned an error, unparseable response, or missing identifier in response body |
| `503`  | Database health check failed at `GET /api/health/db/` |
| `504`  | Upstream (n8n) request timed out |

### Error sources by area

- **Auth** (`/api/login/`, `/api/refresh/`, `/api/logout/`, `/api/me/`) —
  401 on bad credentials or bad token, 400 on missing refresh payload, 500
  only as a last-resort fallback when token generation fails (see
  [authentication.py:360-407](../backend/src/authentication/views/authentication.py#L360-L407)).
- **Password reset** (`/api/password/forgot/`, `/api/password/reset/`) —
  404 if the email is unknown, 400 if the token is missing, wrong, or
  expired. Throttled under the `password_reset` scope.
- **Invites** (`/api/invite/`, `/api/invite/confirm/`) — 400 validation,
  403 if the caller lacks permission for the requested role/scope, 404 if
  the project or client is missing, 400 on invalid/expired confirmation
  token.
- **Users / Roles** — 404 on unknown user id, 400 on missing `role` field.
- **Projects / Clients / Agents / Expertise Areas** — standard DRF CRUD:
  400 on validation (including uniqueness), 403 on permission checks,
  404 on unknown `pk`.
- **Chat sessions / favorites** — 400 if a session already exists on
  create, 404 if the session/favorite target does not exist.
- **Knowledge Base** (proxied to n8n — see views in
  [backend/src/authentication/views/kb_*.py](../backend/src/authentication/views/)) —
  these views have the richest error surface because they touch an
  external service:
  - 400 — missing `project_id`, `hash_id`, or other query parameters
  - 403 — the authenticated user does not have access to the project or KB
    (`assert_user_project_access`, `assert_user_kb_access`)
  - 404 — project not found
  - 500 — `N8N_BASE_URL` or `N8N_KB_KEY` not configured
  - 502 — n8n returned a non-JSON response, raised a
    `RequestException`, or responded without the expected `hash_id`
  - 504 — `requests.Timeout` when calling the n8n webhook (default 10s,
    overridable via `N8N_TIMEOUT`)
  - 207 — only on `PATCH /api/kb/file/update/`, when the replacement file
    was uploaded but the old-file cleanup failed
- **Search** (`/api/search/`) — 500 if n8n is not configured, 504 on
  timeout. Proxied to n8n.
- **Translation** (`/api/i18n/translate/`, `/api/i18n/translate/batch/`) —
  413 when the batch is too large. Backed by AWS Translate.
- **Health** — `/health/` always 200 if the process is up;
  `/api/health/db/` returns 503 if the database is unreachable.

### Validation vs. not-found vs. permission

The codebase is consistent about this split:

- If a required query/body field is **missing or malformed** → 400.
- If the caller is **not authenticated** at all → 401.
- If the caller is authenticated but **not allowed** → 403.
- If the resource referenced by a valid id **does not exist or is not
  visible** to the caller → 404.

Permission errors are raised through
[backend/src/authentication/permissions.py](../backend/src/authentication/permissions.py)
(`assert_user_project_access`, `assert_user_kb_access`) and surface as 403
with a `detail` message.

## 5. Keeping the two spec sources in sync

Because the hand-written [openapi.yml](../openapi.yml) and the `drf-yasg`
output are maintained independently, drift is possible. When changing the
API:

1. Update the view and its `@swagger_auto_schema` decorator — the live
   `/swagger/` page will reflect it on reload.
2. Mirror the change in [openapi.yml](../openapi.yml): path, parameters,
   request body, response schemas, and error statuses.
3. Load `/swagger/` in the browser and skim the affected endpoint to catch
   serializer/schema mismatches before the PR lands.

There is currently no CI lint or diff between the two, so reviewing the
live schema alongside the static file is the safeguard.
